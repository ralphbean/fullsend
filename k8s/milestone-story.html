A field guide to the PoC

From a local cluster to a run that can be trusted

Six milestones trace one question: can a small Kubernetes setup take work from discovery to a recorded result, while keeping execution and credentials inside clear boundaries?

The milestones move from a rebuildable cluster, through durable dispatch and live Jira selection, into remote Fullsend execution and two separate workload identity paths. A controlled stage run now connects Jira selection to real triage execution, writeback, and remote cleanup.

What this evidence says: the PoC demonstrates durable control flow and selected remote execution paths on a local kind cluster. It does not establish OpenShift compatibility, production tenant isolation, high availability, or exactly-once external effects.

Chapter 01 · FoundationVerified

Make the environment repeatable first

Before asking whether dispatch is reliable, make the cluster easy to rebuild and its state easy to recognize.

The goal

Create a local kind environment that can be reset without touching the user's default Kubernetes context or unrelated clusters.

What changed

  • Small, ordered scripts create the named cluster, build this checkout's control image, load configuration, apply PostgreSQL and run a smoke cycle.
  • PostgreSQL uses a PVC. Re-deploying and restarting its Pod preserve data; a deliberate cluster reset replaces the cluster and its database.
  • Ownership marker and dedicated kubeconfig checks guard cluster operations. Reports capture source/build details and redacted diagnostics.

Shortcut & boundary

The tested environment is rootless Podman plus kind. Its default networking is not proof of tenant isolation or NetworkPolicy enforcement. The recorded checks passed twice from reset; they do not characterize production operations.

Chapter 02 · Durable control flowCore path verified

Give work a memory that outlives a Pod

A poll or dispatcher can stop between steps. The database records what was seen, what was selected, and whether a Job was actually cleaned up.

The goal

Build a credential-free fixture loop that discovers work, selects runs, launches independent Kubernetes Jobs, and reconciles the result in a later cycle.

What changed

  • Poll and dispatch cycles persist observations, checkpoints, selected-run sets, attempts, and outcomes in PostgreSQL.
  • Deterministic Job names and UID associations make ambiguous create responses and later reconciliation visible.
  • Capacity and entity-conflict reservations keep waiting or uncertain work from silently disappearing. Job cleanup must be observed before those reservations are released.

Shortcut & boundary

The baseline source and runner are fixtures and stubs, not Jira or an agent. Database-backed tests cover many recovery cases, but process kills and checkpoint-commit uncertainty have not been fault-injected in kind. Durable bookkeeping is not an exactly-once promise. Readers beware: do not copy the PoC's dispatch structure as the target architecture. The intended interface is normal fullsend poll and fullsend dispatch invocations configured to write outputs to PostgreSQL and read inputs from it. Kubernetes Job lifecycle management may live in a separate K8s-specific command/code scope, even when invoked by the same dispatch CronJob.

1. Add a fresh fixture observation

This creates UUID-keyed activity and triggers poll and dispatch cycles. It changes the ignored local fixture file, so each invocation adds another sample.

k8s/kind/inject-observation.sh --profile fixture

2. Follow it into its attempt

PostgreSQL retains the selected run and cleanup result even after the short-lived runner Job is removed.

kubectl --kubeconfig k8s/.local/kubeconfig --context kind-fullsend-poc -n fullsend-control exec statefulset/postgres -- psql -U fullsend -d fullsend -c '
SELECT o.id, o.observation_key, r.harness, r.execution, r.state,
       a.job_name, a.outcome, a.cleanup_state
FROM observations o
LEFT JOIN selected_runs r ON r.observation_id = o.id
LEFT JOIN attempts a ON a.run_id = r.id
ORDER BY o.id DESC, a.number DESC
LIMIT 8;'

The state machine makes retries and cleanup visible; it does not promise exactly-once effects.

Chapter 03 · Live sourceCore path verified

Let Jira nominate work; keep selection trusted

The live source contributes references. The dispatcher fetches the current issue and actor context, then applies the registered repository rules and CEL selection.

The goal

Replace fixture discovery with one bounded Jira project and label while keeping authorization, repository context, and harness choice in trusted configuration.

What changed

  • A controlled issue and a later trigger comment became separate observations and separate CEL-selected stub runs.
  • Replay did not duplicate observations or runs. Role checks, current issue refetch, and repository harness selection run in the live path.
  • A controlled stage run also selected an explicitly enabled triage harness and completed a real Fullsend Job with writeback and verified cleanup.
  • Negative cases—including unauthorized actors, failed pages, and corrupt checkpoints—were exercised against fake Jira responses and real PostgreSQL.

Shortcut & boundary

Jira search returns current issue snapshots, so this is reconciliation polling, not proof that every intermediate transition was delivered. Some negative tests use a fake client; changed config behavior has not been exercised against live Jira. Real execution remains limited to the explicitly enabled triage harness; ordinary selections still use stubs.

Chapter 04 · Remote executionCore path verified

Run Fullsend through a gateway beyond the cluster

A Kubernetes runner can call fullsend run, transfer work to a user-provisioned HyperShell gateway, and retain evidence after the Pod exits.

The goal

Prove useful execution, output validation, and remote cleanup using the same restricted runner shape intended for dispatch.

What changed

  • Gateway probes checked sandbox creation, file transfer, command execution, output hashes, and deletion.
  • A manual UBI runner completed fullsend run with real Vertex inference. A fixture-only gateway-demo also entered the durable dispatcher path.
  • A two-workspace check confirmed that sandbox and provider records stayed within their workspaces. It used synthetic credentials, so it demonstrated resource scoping rather than inference isolation.
  • The controlled stage Jira run used the same remote runner and cleanup path; the run wrote back to Jira only after the allowlisted triage harness completed.
  • Independent cleanup Jobs reconcile remote sandboxes before runner Jobs and their capacity reservations are removed. Cancellation and missing-runner cases use that same gate.

Shortcut & boundary

Runner Jobs share the dedicated gateway's administrative credential, and TLS verification is disabled while the gateway certificate/CA issue remains open. This is not tenant-safe gateway authentication. Only the explicitly enabled triage harness runs for real; ordinary Jira selections continue to use stubs.

Prerequisite: set up the HyperShell gateway

Start at hypershell.app to sign in and get access to your HyperShell account and credentials. Before running setup, have the direct management API URL and OIDC issuer for your environment; the script can use interactive device login or a management bearer-token file. deploy.sh and the probe do not create the external gateway. The setup script creates or reuses the gateway and service account, saves the one-time client secret and OpenShell bundle under ignored k8s/.local/gateway/, and registers the gateway locally. A new gateway also needs a request for a registered ManagedCluster. The probe later installs the saved bundle and secret into kind. If reusing an existing service account, its original client secret must already be saved locally because the API cannot retrieve it. See the setup instructions.

export HYPERSHELL_GATEWAY_NAME="whatever"
export SANDBOX_IMAGE='ghcr.io/fullsend-ai/fullsend-sandbox@sha256:259605fea321353552fdefd3a6a55e8b5c260998dfc5a622ed143e41a429995a'
k8s/kind/07-hypershell-setup.sh \
  --api-url "$HYPERSHELL_API_URL" --issuer-url "$HYPERSHELL_ISSUER_URL" \
  --gateway-name "$HYPERSHELL_GATEWAY_NAME" \
  --gateway-request k8s/.local/gateway/request.json \
  --cluster-name "$HYPERSHELL_CLUSTER_NAME" \
  --service-account-name fullsend-poc

Chapter 05 · Repository identityCore path verified

Trade a short-lived Pod identity for a scoped GitHub token

The runner proves which Kubernetes service account it is. A private mint maps that identity to one configured repository and role before asking GitHub for an installation token.

The goal

Give trusted runner code repository access without putting a GitHub App private key in the runner or remote sandbox.

What changed

  • The mint validates Kubernetes token signature, issuer, audience, expiry, namespace, service account, and UID claims against explicit policy.
  • It requests a GitHub token scoped to immutable repository ID and role permissions, then checks GitHub returned that exact scope.
  • Standalone and dispatcher-created Jobs exchanged projected tokens; rotation, a useful run, output validation, and remote cleanup were observed.

Shortcut & boundary

This kind PoC has no server-side Job admission policy. Job creation can select namespace service accounts, so the launcher remains trusted code. Offline JWT checks cannot revoke a deleted Pod's assertion immediately, and minted GitHub tokens live until their own expiry.

Prerequisite: create and install a GitHub App

The App is required for this milestone's private mint and for the optional real-triage path in chapter 3; it is not needed for milestone 4's gateway probe or fixture demo. Create a private app under your personal GitHub account from New GitHub App; see GitHub's registration guide. Grant repository Contents: read-only and Issues: read and write; Metadata read is enabled by default. This PoC does not use GitHub App webhook events.

Choose Install App and install it on only the repository you own that is configured for the live profile. The current example is ralphbean/jira-triage-test; if you use a different repository, update the live repo configuration and mint allowlist to match. GitHub's installation guide describes the flow.

Find GITHUB_APP_ID on the app's General settings page. Find GITHUB_APP_INSTALLATION_ID at the end of the installation's Configure page URL under account Settings → Applications → Installed GitHub Apps. Use the repository's OWNER/REPOSITORY for GITHUB_REPOSITORY. Generate and download a PEM from the app's Private keys settings, then set GITHUB_APP_PRIVATE_KEY_FILE to its local path. Keep the PEM private and out of the repository; see GitHub's private key guide.

With gh authenticated for that repository, read its immutable numeric ID and export these values for the commands below. The numeric repository ID is derived from GitHub; it is not the App ID.

export GITHUB_APP_ID='APP_ID_FROM_GENERAL_SETTINGS'
export GITHUB_APP_INSTALLATION_ID='ID_AT_END_OF_INSTALLATION_URL'
export GITHUB_REPOSITORY='OWNER/REPOSITORY'
export GITHUB_REPOSITORY_ID="$(gh api "repos/$GITHUB_REPOSITORY" --jq .id)"
export GITHUB_APP_PRIVATE_KEY_FILE="$HOME/path/to/downloaded-private-key.pem"

Chapter 06 · Inference identityVerified

Give inference its own workload identity path

Repository access and cloud inference use separate projected tokens and separate trust decisions. Neither needs a static service-account key.

The goal

Federate a kind service-account identity to Google, reject an ungranted identity, and keep a real remote inference run working while its assertion rotates.

What changed

  • After rebuilding kind, the current public JWKS was uploaded to the existing WIF provider. The authorized identity completed Vertex inference before and after token rotation; the wrong runner identity was denied.
  • A Fullsend/HyperShell run refreshed the inference-only assertion into the active sandbox, observed its rotation, called Vertex, and persisted validated output.
  • The tests used existing cloud resources; no cloud pool, provider, service account, API, or IAM resource was created or destroyed.

Shortcut & boundary

A kind reset changes signing keys, so the existing provider's JWKS must be refreshed before the next run. This does not prove production network isolation or OpenShift compatibility. Inference can incur normal Vertex charges; the optional OpenTofu module remains unapplied.

Before you start: create a PoC Google Cloud identity setup

You need a Google Cloud project with billing enabled for Vertex. Use a project you can administer or create a dedicated PoC project first. Your gcloud identity needs permission to enable APIs, create workload identity pools/providers and service accounts, and grant project and service-account IAM. See Google's Kubernetes Workload Identity Federation guide.

Run these from the repository root and keep the same terminal open. Use a unique project ID; the pool, provider, and service-account names below are PoC examples.

export GCP_PROJECT_ID='YOUR_GCP_PROJECT_ID'
export GCP_PROJECT_NUMBER="$(gcloud projects describe "$GCP_PROJECT_ID" --format='value(projectNumber)')"
export GCP_WIF_POOL='fullsend-kind-poc'
export GCP_WIF_PROVIDER='kind-local'
export GCP_INFERENCE_SERVICE_ACCOUNT_ID='fullsend-poc-inference'
export GCP_INFERENCE_SERVICE_ACCOUNT="${GCP_INFERENCE_SERVICE_ACCOUNT_ID}@${GCP_PROJECT_ID}.iam.gserviceaccount.com"
gcloud config set project "$GCP_PROJECT_ID"

Enable the APIs used for IAM federation and Vertex inference:

gcloud services enable \
  cloudresourcemanager.googleapis.com \
  iam.googleapis.com \
  iamcredentials.googleapis.com \
  sts.googleapis.com \
  aiplatform.googleapis.com \
  --project="$GCP_PROJECT_ID"

With the owned kind cluster running, capture its OIDC issuer and public signing keys. The JWKS is public and stays in the ignored local directory.

mkdir -p k8s/.local/gcp
export GCP_K8S_ISSUER="$(kubectl --kubeconfig k8s/.local/kubeconfig --context kind-fullsend-poc get --raw /.well-known/openid-configuration | jq -er .issuer)"
kubectl --kubeconfig k8s/.local/kubeconfig --context kind-fullsend-poc get --raw /openid/v1/jwks > k8s/.local/gcp/kind-jwks.json

Create a dedicated pool and OIDC provider. The provider maps the Kubernetes subject and accepts only the inference ServiceAccount in fullsend-runner.

gcloud iam workload-identity-pools create "$GCP_WIF_POOL" \
  --project="$GCP_PROJECT_ID" --location=global \
  --display-name="Fullsend kind PoC" \
  --description="PoC workload identity pool for kind inference"

gcloud iam workload-identity-pools providers create-oidc "$GCP_WIF_PROVIDER" \
  --project="$GCP_PROJECT_ID" --location=global \
  --workload-identity-pool="$GCP_WIF_POOL" \
  --issuer-uri="$GCP_K8S_ISSUER" \
  --attribute-mapping='google.subject=assertion.sub' \
  --attribute-condition="assertion['kubernetes.io']['namespace'] == 'fullsend-runner' && assertion.sub == 'system:serviceaccount:fullsend-runner:runner-inference'" \
  --jwk-json-path=k8s/.local/gcp/kind-jwks.json

Create the inference service account, grant it the Vertex and Service Usage roles, then allow only the projected inference ServiceAccount to impersonate it. These commands create no service-account key.

gcloud iam service-accounts create "$GCP_INFERENCE_SERVICE_ACCOUNT_ID" \
  --project="$GCP_PROJECT_ID" \
  --display-name="Fullsend kind PoC inference"

gcloud projects add-iam-policy-binding "$GCP_PROJECT_ID" \
  --member="serviceAccount:$GCP_INFERENCE_SERVICE_ACCOUNT" \
  --role=roles/aiplatform.user
gcloud projects add-iam-policy-binding "$GCP_PROJECT_ID" \
  --member="serviceAccount:$GCP_INFERENCE_SERVICE_ACCOUNT" \
  --role=roles/serviceusage.serviceUsageConsumer

gcloud iam service-accounts add-iam-policy-binding "$GCP_INFERENCE_SERVICE_ACCOUNT" \
  --project="$GCP_PROJECT_ID" \
  --member="principal://iam.googleapis.com/projects/${GCP_PROJECT_NUMBER}/locations/global/workloadIdentityPools/${GCP_WIF_POOL}/subject/system:serviceaccount:fullsend-runner:runner-inference" \
  --role=roles/iam.workloadIdentityUser

These are create-once commands; skip resource creation if you are reusing existing resources. A kind reset rotates signing keys, so refresh the provider's JWKS with step 1 before running the probes.
