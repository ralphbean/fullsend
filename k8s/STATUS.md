### Milestone 4: dispatcher integration and current blocker

- The exact fixture harness `gateway-demo` can now be selected by the local observation poller and launched by the dispatcher as a UBI10 runner Job. It uses the same pinned sandbox image and manual demo fixture as the earlier successful run. Its sandbox name derives from the durable attempt Job name. The runner writes intent, validated output, SHA-256, and deletion results to the evidence PVC.
- A separate `fs-clean-<run>-<attempt>` Job lists the gateway and deletes the derived sandbox if it is present. Only confirmed remote absence lets the dispatcher delete the runner Job; only subsequent confirmation that the runner Job is gone completes the attempt and releases its reservation. A missing runner Job or an explicit `cancel RUN_ID` follows the same cleanup gate and becomes a failed run. Cleanup Jobs retry transient gateway failures; a terminal failure retains the reservation. `08-gateway-cleanup.sh` also verifies dispatcher-owned sandboxes before kind reset or destroy.
- Database-backed integration tests exercised a lost Job-create response, a successful runner, a missing runner, a failed cleanup Job, an in-progress cleanup retry, a foreign cleanup label, and explicit cancellation. They verified that capacity stayed reserved until the independent cleanup Job succeeded. A separate test ran the cleanup command through a fake OpenShell binary and checked that `cleanup.json` was written only after the sandbox disappeared.
- The first in-kind dispatcher run created `fullsend-runner/fs-poc-12-1` and its cleanup Job. Both failed before any sandbox intent was written because the managed HyperShell identity hostname returned DNS `NXDOMAIN` from both the host and a kind Pod, while an unrelated public hostname resolved. The database currently has attempt 12 in `cleanup` with outcome `failed`, cleanup pending, and its selected run still `reserved`. The cleanup Job was created by the earlier control image with no retries; after managed DNS recovers, delete that failed Job and let the updated dispatcher recreate it. Preserve the kind cluster and evidence PVC until remote absence is verified. The source observation was UUID keyed, so replay remains duplicate-free.
- The revised dispatcher keeps a terminal runner Job for log inspection until the remote cleanup Job succeeds. That revision and the three-retry cleanup template passed local tests but have not completed a live gateway run while managed DNS is unavailable. The live Jira profile still launches stub Jobs. Two workspaces and provider/credential separation are still unverified; the dedicated gateway continues to use shared administrative access.

### Milestones 5–6: identity paths

- Milestone 5 has no implementation evidence. The Kubernetes service-account token used below has a **Google WIF audience**, not a mint audience, and it cannot stand in for a scoped GitHub installation token.
- For milestone 6, in-cluster Job `fs-wif-probe-a1214166` used a projected token from a dedicated inference Kubernetes service account, exchanged it through Google STS, impersonated a scoped inference cloud service account, and received a Claude Haiku 4.5 response from Vertex. Its ignored local log is `k8s/.local/gcp/wif-probe-a1214166.log`. The successful `poc4` run then copied an inference-only assertion and external-account ADC configuration into its remote sandbox; it used no static service-account key in that run. The token was a per-run copy, so the four-minute run did **not** test rotation or continued inference after expiry.

The manual inference fixture and its rendered Job contain local cloud configuration under ignored `k8s/.local/`; the success is recorded here without committing those inputs. A repeatable checked-in inference demo script and all remaining milestone 4 and 6 acceptance checks are still required. The local kind network is not evidence of production NetworkPolicy enforcement, and none of these results establishes OpenShift compatibility, tenant isolation, high availability, or exactly-once external effects.
