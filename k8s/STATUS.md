## Evidence and limits

### Architectural caveat: do not copy the PoC's dispatch structure

**Readers beware: the verified PoC behavior does not validate its package or command boundaries as the long-term design.** `fullsend k8s-poc dispatch` currently owns PostgreSQL selection/reservations, Kubernetes Job creation, and Job reconciliation in one PoC-specific path. The intended direction is to retain normal `fullsend poll` and `fullsend dispatch` invocations, configured by a CLI flag or configuration to write outputs to PostgreSQL and read inputs from PostgreSQL.

Kubernetes Job lifecycle management may instead be a separate K8s-specific command and code scope, invoked by the same dispatch CronJob if useful but separate from the `fullsend dispatch` invocation. The exact command boundary and database interfaces remain design work. The current PoC intentionally takes shortcuts here; **do not use its structure as the implementation template.**

### Major compatibility caveat: OpenShell client and HyperShell gateway

Fullsend's run path shells out to an `openshell` binary supplied by its execution environment; it does not negotiate a client version with the gateway. The verified HyperShell path depends on the host preflight and runner image using the compatible `0.1.2-rhaiv.0` client. The PoC layers that client over the checkout-built runner and rejects a different host version. This is an integration constraint of this gateway setup, not a general guarantee that Fullsend's standard runner image works with HyperShell. Recheck the exact client/gateway pairing if either side changes.

### Milestone 5: private Kubernetes identity mint

- `cmd/mint` now serves a separate `POST /v1/kubernetes/token` path when `KUBERNETES_MINT_CONFIG_FILE` is configured. It validates the Kubernetes JWT signature, issuer, mint-only audience, lifetime, service-account subject, namespace and UID claims, then binds that identity to configured repository IDs, installation, role, and allowed levels. The configured public JWKS is read on each request; private signing keys are not exported from kind.
- `internal/mintcore` requests GitHub installation tokens by immutable repository ID and role permissions. The handler returns a token only after GitHub's response confirms the exact repository ID and permission map. HTTPS is required between runner and mint; the App PEM is mounted only into the mint Pod.
- The runner client rereads the projected JWT file on every exchange attempt. Its Git credential helper refreshes the GitHub token on a four-minute interval, atomically replaces the credential file, and removes credentials and cancels the active run on refresh denial. Environment values already captured by an agent process cannot be changed, so this refresh covers subsequent Git operations rather than already-running API clients.
- On 2026-10-07, `fs-mint-9d1ccd24` exchanged a 600-second projected mint-audience token for an installation token restricted to the configured repository and coder permission set, including `packages:read`. Kubelet rotated the projected token; the second exchange returned the same exact repository and permission scope. The Job was deleted after completion. Its ignored local log is `k8s/.state/mint-probe-fs-mint-9d1ccd24.log`; it contains only a generic success line. Unit tests cover wrong issuer, audience, namespace, service-account role, repository, expired token, broader or incomplete GitHub grants, retry token rereads, and refresh denial.
- Dispatcher attempt `fs-poc-3-1` created or reused the repository/triage ServiceAccount, mounted only the 600-second mint-audience token and CA into the runner container, and completed a real `fullsend run gateway-demo` through the private mint. The runner received a repository-scoped triage installation token, completed the agent successfully, validated its output, and recorded sandbox deletion. Independent Job `fs-clean-3-1` verified remote absence before the dispatcher released the reservation. `11-dispatch-gateway-demo.sh` checks the ServiceAccount labels, disabled automatic API token mount, Job identity, token audience/lifetime, and runner env wiring.
- The dispatcher uses a separate `launcher` ServiceAccount with namespace-scoped permission to create/read/delete runner Jobs and create/read ServiceAccounts. The controller emits a fixed validated Job template and untrusted agents never receive this API identity. Kubernetes Job creation itself permits selecting namespace ServiceAccounts; this local PoC has no server-side admission policy and does not establish tenant-safe production isolation.
- Kubernetes JWT verification is offline: a deleted Pod's projected JWT remains valid until expiry. A minted GitHub token also remains valid until GitHub's own expiry. The probe establishes the local kind mint and rotation path; it does not establish production cluster isolation or immediate revocation.
